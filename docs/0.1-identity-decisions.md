# 0.1 — Identity foundation: decisions and field map

Status: **settled**, 2026-08-05. This is the written output of `todo.md` task 0.1
("decide + document, before touching any model"). Nothing in `0.2`–`0.5` should
contradict this file; if it needs to, change this file first and say why.

Everything below was checked against the code as it stands on
`feature/google-auth-qr-redirect`, not against the plan's assumptions. Where the
two disagreed, the disagreement is recorded rather than quietly resolved.

---

## Decision log

### D1 — `UserProfile` lives in `apps/user/`, alongside `User`
Confirmed, no change from the plan. O2O to `User`, `related_name="profile"`, with
`primary_key=True` on the relation so the profile's pk *is* the user's pk — no
surrogate id, and 1:1 enforced structurally rather than by convention.

### D2 — The identity anchor is `User.pk`, but it is **not** a UUID
The guiding decisions say "Identity anchor = `User.pk` (UUID)". That is factually
wrong about this codebase: `apps/user/migrations/0001_initial.py` creates `User`
with a `BigAutoField` pk, and `DEFAULT_AUTO_FIELD` is `BigAutoField`.

**Resolution:** leave the pk alone and add `User.public_id = UUIDField(unique=True,
default=uuid4, editable=False)`.

The anchor requirement — stable across student → alumnus → staff, never a login
handle — is already satisfied by `BigAutoField`. The only property UUID adds is
non-enumerability, which matters solely where the identifier is *exposed*
(Phase 7's QR credential, public URLs). A second field buys that for one
migration. Migrating the pk itself would rewrite every FK in the project plus
allauth, `django_admin_log`, and session tables, on live data, for a property a
separate column provides.

Note the role models already use UUID pks (`AlumniProfile.id`, `Employee.id`,
`QRCode.id`), so external exposure of *those* is already fine. `public_id` closes
the gap at the `User` level.

### D3 — Membership moves off `AlumniProfile` into its own model on `User`
This **overrides** the `todo.md` line "membership fields … stay on
`AlumniProfile`". Three requirements in the plan itself defeat that placement:

1. **Phase 1.6's Student tier is free and pre-graduation.** A student has no
   `AlumniProfile` — that record is what they gain *at* graduation. Membership
   fields on `AlumniProfile` mean the student on-ramp cannot exist, which is the
   funnel the identity model was built for (0.1's own third bullet).
2. **Phase 1.4 wants renewal/upgrade history visible.** History is rows, not
   fields. `membership_expiry` overwritten in place has no history.
3. **Phase 2.6 wants installment accumulation toward a target rung.** That needs
   a record to accumulate *against*.

**Resolution:** a `Membership` model, FK (not O2O) to `User` so history
accumulates, with the current membership resolved by manager method rather than a
denormalized pointer.

```python
class Membership(models.Model):
    user       = FK(User, related_name="memberships")
    tier       = FK(MembershipTier, on_delete=PROTECT)
    status     = pending | active | expired | cancelled
    started_on = DateField()
    expires_on = DateField(null=True)      # null = lifetime
    is_lifetime = BooleanField(default=False)
    membership_number = CharField(unique=True, null=True)
    payment_frequency = once | monthly | quarterly | annually
    # issued items follow the membership, not the person
    card_issued = certificate_issued = certificate_sent = lapel_badge_issued = Bool
    certificate_generated_at = DateTimeField(null=True)
```

`AlumniProfile` is left purely academic: qualification, graduation data,
employment, slug.

**Consequence for 1.3's service layer:** `renew_membership()`,
`upgrade_to_lifetime()` and `assign_membership_tier()` currently live as methods
on `AlumniProfile` (`apps/home/models.py:742-800`) that mutate fields in place.
They become the service layer operating on `Membership` rows. This is a *net
simplification* of 1.3, not extra work — the "one door" was going to have to be
written anyway.

**Cost, stated honestly:** 0.3's migration grows a third table and the data
migration must synthesise a `Membership` row per alumnus who currently has tier
or expiry data. Reversible, isolated, and the backfill is mechanical.

### D3a — The `Student` role, and what graduation actually does
`apps/student/models.py` is currently an empty stub. It stays thin, on the same
`User`, mirroring `AlumniProfile`'s shape:

```python
class StudentProfile(models.Model):
    user            = OneToOneField(User, related_name="student_profile")
    registration_no = CharField(unique=True)
    faculty         = FK("staff.Faculty", null=True)
    programme       = FK("home.Qualification", null=True)   # what they're reading for
    year_of_study   = PositiveSmallIntegerField(null=True)
    expected_completion = DateField(null=True)
    is_active       = BooleanField(default=True)
```

Graduation is then **additive, not migratory**: the same `User` gains an
`AlumniProfile`, the `StudentProfile` is marked inactive (not deleted — it is the
history), and the existing free student `Membership` is upgraded in place through
1.3's service layer. No re-registration, no record copying, no new identity. This
is the entire payoff of anchoring on `User`, and it only works because D3 put
membership on `User` rather than on the alumni record.

`AlumniProfile.student_reg_no` becomes redundant for anyone who came through this
path, but stays — it is the only reg-no source for alumni who register directly
without ever having a `StudentProfile` (everyone pre-dating the system).

### D4 — `date_of_birth` is nullable on `UserProfile`
`AlumniProfile.date_of_birth` is NOT NULL today; `Employee.date_of_birth` is
nullable. A merged column must accept null or the employee backfill fails on the
first row. Requiredness moves to `AlumniProfileForm`, where it belongs — it is an
Association membership-form rule, not a property of being a person.

### D5 — `photo` and `google_photo_url` move to `UserProfile`
Both are person-level. `google_photo_url` is currently duplicated on **both**
`User` (`apps/user/models.py:50`) and `Employee` (`apps/staff/models.py:347`);
after the move it exists once, on the profile, and the `User` copy is dropped.

**Migration hazard:** `Employee.photo` uses `employee_photo_upload_path`, which
keys the filename to the *employee* UUID (`employee_photos/<employee-uuid>.<ext>`,
commit e9bdd48). Moving the field to `UserProfile` changes the path function, so
the data migration must relocate existing files, not just repoint rows. Small
volume today — do it properly now rather than leaving orphans.

### D6 — Employment stays split
`AlumniProfile.current_employer` / `employment_position` (external employment,
captured on the Association's form) are **not** unified with `Employee.position` /
`department` (internal UoN appointment). They describe different things and a
staff-alumnus legitimately has both. Both stay on their role models.

### D7 — One honorific vocabulary
There are currently **four** overlapping title vocabularies:
`AlumniProfile.TITLE_CHOICES` (titlecase `Mr`/`Dr`), `Employee.HonorificChoices`
(lowercase `mr`/`dr`), and separate `TITLE` tuples on `home.Executive` and
`home.Secretariat` (uppercase `MR.`/`DR.`). One `Honorific` TextChoices in
`apps/user/`, lowercase keys, becomes canonical; the rename migration maps the
existing values into it. `Executive`/`Secretariat` are display-only models and can
be repointed opportunistically, not as a blocker.

**The opt-in defaults do not ride across.** `receive_newsletter` and
`receive_sms_alerts` both default `True` today. Consent under the Data Protection
Act 2019 cannot be inherited as pre-granted, so the new fields default `False` and
the backfill must **not** copy the old `True` values. Existing members re-consent
at next login or via a one-off campaign — an Association decision, flagged below.

### Stays on `AlumniProfile`
`qualification`, `graduation_year`, `graduation_institution`,
`other_institution_name`, `other_institution_qualification`, `name_at_graduation`,
`student_reg_no`, `faculty`, `current_employer`, `employment_position`,
`registration_date`, `last_updated`, `is_active`, `slug`.

Membership fields and issued-item flags leave for `Membership` (D3).

### Stays on `Employee`
`staff_id`, `academic_rank`, `staff_track`, `department` / `service_unit` /
`research_unit`, `position`, `employment_type`, `date_joined`, `is_active`,
`qr_code_image`, `slug`.

### Blocking pre-migration check
`AlumniProfile.id_passport_no` and `Employee.national_id` are **both `unique=True`
on separate tables**. Merging them into one unique column on `UserProfile`
succeeds only if no two *different* Users hold the same number. That is legal
today and will hard-fail the backfill.

The local dev DB already has **one User holding both an `AlumniProfile` and an
`Employee` row** — the staff-alumnus case is real, not hypothetical. Run the
dedup audit against **production** before writing the data migration; the local
DB is not representative.

## Tier taxonomy

### What is actually seeded vs. what the plan says

Read from the **local dev** `db.sqlite3` — production must be re-checked before
any of this is treated as fact.

| Seeded name | Fee | `tier_type` | `duration_months` | Verdict |
|---|---|---|---|---|
| Corporate Membership | 1,000,000 | corporate | **0** | 0 ⇒ `is_lifetime()` true; plan says recurring |
| Platinum Life | 500,000 | life | 0 | **not in the plan's taxonomy** |
| Diamond Life | 250,000 | life | 0 | **not in the plan's taxonomy** |
| Gold Life | 100,000 | life | 0 | matches |
| Silver Life | 50,000 | life | 0 | matches |
| Bronze Life | 25,000 | life | 0 | matches |
| Honorary | 3,000 | honorary | **0** | 0 ⇒ lifetime; plan says recurring |
| Full Annual | 2,000 | annual | 12 | matches |
| Student Annual | **500** | **annual** | 12 | plan says free/nominal, own category |

### Resolutions
- Add `student` to `TIER_TYPES`. Student is a pipeline tier with its own
  conversion rules, not an annual variant.
- Set Honorary and Corporate to real periods so they stop silently reading as
  lifetime. `duration_months=0` currently means "lifetime" via
  `MembershipTier.is_lifetime()`, so both are today permanent by accident.
- Add `ladder_rank` (small int, null = off-ladder) to encode the monotonic
  upgrade path Annual → Bronze → Silver → Gold → Corporate. `order` is display
  ordering and cannot carry this — Phase 2.6's installment upgrades need to
  resolve "the next rung's price" programmatically.
- `payment_frequency` belongs on `Membership` (the member's choice), **not** on
  `MembershipTier` (a property of the product).

### Bug found while mapping this
`MembershipTier.get_expiry_date()` (`apps/home/models.py:583`) computes duration as
`timedelta(days=self.duration_months * 30)`. A 12-month membership therefore
expires after 360 days and drifts ~5 days earlier on every renewal. Use calendar
month arithmetic (`dateutil.relativedelta`) when the service layer is built in
1.3. Not urgent while activation is manual; wrong the moment renewals automate.

## Open — the Association's call, not ours
These block "done", not progress. Build proceeds with the values above as
provisional.

1. **Platinum (500k) and Diamond (250k)** — fold into the ladder above Gold, or
   retire? They exist in data and not in the brochure taxonomy.
2. **Honorary and Corporate billing periods** — annual, or something else?
   "Conferred but still paid" needs a period to be payable.
3. **Corporate is organizational**, but membership attaches to a `User` (a
   person). Multiple named reps under one corporate membership needs a shape
   decision. Deferred to Phase 1.6 — it does not block 0.2–0.5.
4. **Re-consent for existing members** — how the opt-in flip is communicated.
5. **Retention rule and the soft-delete vs. right-to-erasure reconciliation**
   (cross-cutting in `todo.md`, unchanged and still open).

## What this implies for 0.3's migration order
1. Rename pass — `RenameField` only, no data movement, per role model.
2. Create `UserProfile` + `User.public_id`; backfill from `AlumniProfile`, then
   `Employee` (alumni first: it has the richer person data).
3. Create `Membership`; synthesise rows from existing `AlumniProfile` membership
   fields.
4. Relocate `photo` files (D5).
5. Remove moved fields from the role models.

Five migrations, not one, so a failure is isolated and each step is reversible.

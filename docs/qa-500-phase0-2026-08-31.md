### 3d. `SubdomainRoutingMiddleware` — full source, `main/middleware.py:4-30`

```python
class SubdomainRoutingMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        host = request.META.get('HTTP_HOST', '').lower()
        if ':' in host:
            host = host.split(':')[0]

        base = settings.SUBDOMAIN_DOMAIN

        if host == base:
            subdomain = None                      # apex: uonalumni.or.ke / lvh.me
        elif host.endswith(f'.{base}'):
            subdomain = host[:-(len(base) + 1)]   # 'staff', 'students', 'www'
        else:
            subdomain = None                      # IPs, localhost, unknown hosts

        request.subdomain = subdomain

        # Keep allauth on the shared ROOT_URLCONF on every subdomain —
        # this is the common /accounts/ login path.
        if not request.path.startswith('/accounts/'):
            urlconf_map = getattr(settings, 'SUBDOMAIN_URLCONFS', {})
            request.urlconf = urlconf_map.get(subdomain, settings.ROOT_URLCONF)

        return self.get_response(request)
```

Ordering in `MIDDLEWARE` (`main/settings.py:158-177`): it sits after `AccountMiddleware` and before `CommonMiddleware` — and, notably, **before** `AuthenticationMiddleware`, so `request.user` does not exist during URLconf selection. Fine as written, but it constrains any proposed fix.

## 4. Test-database strategy

### Current, as configured

There is no test-specific settings module. `manage.py test` loads `main.settings`, whose `DATABASES` branch is evaluated at **import** time under `DEBUG=True` (`main/settings.py:223-242`) and resolves `DATABASE_URL` from `.env`:

```
DATABASE_URL=postgresql://<user:pass>@localhost:5432/uon_alumni_II
```

So Django creates and destroys **`test_uon_alumni_II` on local Postgres**. Neon is not reachable from this configuration at all — the production URL lives in the server's environment, not this `.env`. The 281 MB `db.sqlite3` at repo root is dormant (it is only the fallback when `DATABASE_URL` is unset) and has not been touched.

### The DEBUG wrinkle Phase 1 must account for

Django's test runner sets `settings.DEBUG = False` at runtime, but every `if DEBUG:` branch in `settings.py` — `ALLOWED_HOSTS`, `DATABASES`, `SUBDOMAIN_DOMAIN`, `QR_SCAN_ORIGINS` — already ran at import with `DEBUG=True`. Under test, therefore:

- `SUBDOMAIN_DOMAIN` is **`lvh.me`**, not `uonalumni.or.ke`
- `ALLOWED_HOSTS` is `['localhost', '127.0.0.1', 'lvh.me', '.lvh.me']`, plus `testserver` appended by the runner

Consequence: Phase 1 tests must pass `HTTP_HOST='lvh.me'`, `'staff.lvh.me'`, `'students.lvh.me'`. The test client's default `testserver` falls through the middleware's `else` branch to `subdomain = None` → `main.urls`, which would silently exercise only the public host and never touch the staff or students URLconfs — the failure mode would be a suite that passes while testing nothing.

### Proposal — keep local Postgres. No settings change.

Recommended because it is already the configured behaviour (zero settings edits, so the "no settings changes" constraint holds trivially), it cannot reach Neon, and it matches production's engine.

**A Neon test branch is not recommended:** it needs network and credentials on every run, is markedly slower, and introduces a real chance of a mistyped URL pointing at production — against a task whose whole point is not writing to real data.

**SQLite is not recommended**, because it would mask exactly the class of 500 we are hunting:

- **Aborted-transaction errors.** After any failed statement inside `atomic()`, Postgres poisons the transaction — every subsequent query raises `current transaction is aborted`. SQLite carries on. A swallowed `IntegrityError` inside an atomic block is a 500 on Postgres and invisible on SQLite.
- **`LIKE` case-sensitivity.** SQLite's `LIKE` is case-insensitive for ASCII; Postgres' is not. Lookups in the profile-claim flow (`_resolve_claim_match`, `apps/home/views.py:1214`) could behave differently.
- **Over-length string writes.** Postgres raises `value too long for type character varying(n)`; SQLite silently accepts. `apps/qr_manager/views.py:24` truncates `user_agent` to 255 defensively, but other write paths may not.
- **Strict `GROUP BY` / `DISTINCT ON` / annotated `order_by`** — Postgres rejects what SQLite tolerates, relevant to the analytics and export views.
- Type strictness generally, and `USE_TZ` datetime handling.

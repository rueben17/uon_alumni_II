BUGS / CORRECTNESS (fix first)
--------------------------------------------------------------------------------

1. [HIGH] Reflected XSS via `track` GET param in Alpine x-data
   File: templates/staff/all_uon_staff.html:25
   x-data="{ track: '{{ selected_track|default:'' }}' }"
   Django's default autoescaping is the wrong context for a value embedded in
   a JS string. The browser HTML-decodes the attribute before Alpine
   evaluates it as JS, so a crafted URL like:
     ?track=x',evil:(alert(1),0)
   breaks out of the string and runs arbitrary JS for anyone who opens the
   link.
   Fix: use |escapejs, or better, pass the value via {{ selected_track|json_script:"selected-track" }}
   and read it from there in Alpine. Also allowlist `track` server-side
   against Employee.StaffTrack.choices before it ever reaches a template.

2. [HIGH] HTMX self-nesting on every filter/search/pagination interaction
   Files: templates/staff/all_uon_staff.html:26-30
          templates/staff/partials/employee_table.html:1, 51, 69, 83
   hx-target and hx-select both resolve to "#staff-table-container", and the
   partial Django returns for HTMX requests already has that id on its own
   root <section>. With the default innerHTML swap, each interaction nests a
   duplicate-id copy of the table section inside the original instead of
   replacing it -- breaks layout (doubled padding / min-h-screen) and any
   future getElementById / hx-target lookup against that id.
   Fix: drop hx-select (redundant -- the response already IS the fragment)
   or switch to hx-swap="outerHTML".

3. [FIXED 2026-08-06] Navbar/banner/footer commented out on the profile-update page
   File: templates/staff/profile_update.html (top include block ~line 7-8,
         bottom footer include ~line 92)
   Was wrapped in {% comment %} rather than removed. Uncommented during the
   nav/footer wiring pass; the page now has Sign Out and normal navigation
   like every other page.

4. [MED] Track/unit filter combo isn't cross-validated, client or server side
   Files: templates/staff/all_uon_staff.html:70, 77, 84
          apps/staff/views.py:104-124
   Alpine only disables mismatched <option>s on the track select's `change`
   event -- never on initial page load. A stale/shared/back-navigated URL
   like ?track=teaching&unit=service:5 renders a disabled-yet-selected
   option, and the server ANDs both filters, silently returning "No staff
   found" with no indication the combo itself is contradictory.

5. [MED] hx-trigger override drops the implicit `submit` trigger
   File: templates/staff/all_uon_staff.html:30
   The explicit hx-trigger="keyup ..., change ..." on the <form> replaces
   htmx's default `submit` binding, so clicking "Apply" or pressing Enter
   does a full native page reload while every other interaction (typing,
   changing selects) stays AJAX. Inconsistent, easy to miss.

6. [MED] "Public staff directory" docstring vs. login-gated view
   Files: apps/staff/views.py:75-78  vs  templates/snippets/navbar.html
   EmployeeListView is LoginRequiredMixin, but its own docstring calls it a
   "Public staff directory," and the navbar links to it from the
   unauthenticated main-site branch. Anonymous visitors get bounced to
   login instead of the directory the nav implies is open. Confirm which
   behavior is actually intended.

7. [LOW / needs manual test] Possible event-ordering race
   File: templates/staff/all_uon_staff.html:49
   Alpine's x-on:change cleanup handler on #id_track and htmx's own
   "change from:#id_track" trigger both listen on the same native event
   with no guaranteed order; if htmx fires first, a stale unit= value could
   ride along with a newly-changed track=, producing an unexpectedly empty
   result. Verify by clicking through the filter in a browser rather than
   fixing blind.

ARCHITECTURE / FUTURE WORK
--------------------------------------------------------------------------------

13. Shared base model for Employee / AlumniProfile / (future) Student
    apps/staff/models.py's Employee and apps/home/models.py's AlumniProfile
    already duplicate a large chunk of the same personal/contact fields
    independently, and a Student model will very likely repeat the same
    shape again:
      - honorific/title (courtesy title)
      - given_name / first_name, middle_name, family_name / surname
      - date_of_birth
      - national_id / id_passport_no
      - phone_number / phone_mobile, alt_phone_number / phone_alt
      - slug (AutoSlugField off the name), is_active
      - created_at/updated_at vs. registration_date/last_updated
      - the same full_name/display_name property pattern and
        get_absolute_url() shape
    Proposal: pull the common fields + properties into a single abstract
    base model (e.g. `PersonProfile`) that Employee, AlumniProfile, and the
    future Student model all subclass, so each concrete model only adds
    what's actually specific to that role (staff_track/department for
    Employee; qualification/graduation details for AlumniProfile). Avoids
    the three models drifting out of sync on field names/validation for
    what is conceptually the same data. This is a real migration (moving
    live fields onto an abstract parent), not a quick edit -- plan it as
    its own task rather than folding it into an unrelated change, and
    decide where it lives (a shared app, or apps/user/ alongside the User
    model) before touching either existing model.

14. Friendlier Google OAuth failure page + surfaced diagnostics
    allauth renders its generic socialaccount/authentication_error.html on
    any callback failure (e.g. the "Third-Party Login Failure" page a user
    hit after sign-out/sign-in), and swallows the real exception in the
    process -- only a stock message reaches the user, and nothing reaches
    us. Two parts:
      - Override socialaccount/authentication_error.html with a branded,
        reassuring page (link back to /accounts/google/login/) instead of
        allauth's default.
      - Override CustomSocialAccountAdapter.authentication_error() (apps/
        user/adapter.py) to logger.exception() the real error allauth
        passes it, so it's actually diagnosable (journalctl at minimum;
        wire to Django's AdminEmailHandler/ADMINS or a service like Sentry
        if we want proactive notification instead of checking logs after
        the fact -- needs SMTP configured first, which isn't set up yet).

15. Session/idle timeout re-authentication on data-sensitive user-end pages
    Alumni-facing edit views (AlumniProfileUpdateView, AlumniMembershipUpdateView
    /renew-upgrade, AlumniProfileDeleteView -- national_id, DOB, phone, payment
    history) currently accept a POST any time the Django session is still
    alive, however long the tab's been sitting open with the form loaded. No
    idle check ties the edit itself to how recently the user actually
    authenticated.
    Proposal: stamp request.session['auth_time'] = now() in the login/signup
    adapter hooks (apps/user/adapter.py), then a small mixin/decorator on the
    sensitive AlumniProfile views that, on POST, checks elapsed time against
    a threshold (e.g. 15 min) and -- if stale -- redirects to re-auth via
    Google (carrying `next` back to the same form) instead of accepting the
    edit. Same "step-up re-auth" shape as GitHub's sudo mode / Django admin's
    re-login-on-timeout, scoped only to the alumni user-end forms listed
    above, not staff.

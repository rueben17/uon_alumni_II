## Targets that did not reproduce

Both are documented in the report with the source quoted that proves why.

- **Target 1 — the staff mis-gating cluster does not 500.** All four views fail *closed* with a 404: `CompleteProfileView` (`views.py:258`), `ProfileUpdateView` (`views.py:281`), `ProfileDeleteView` (`views.py:303`, `:307`) and `download_staff_qr_code` (`views.py:407`) all use `get_object_or_404` or an empty-queryset lookup. Five passing tests pin this. The gating is still wrong in *kind* — 404 where `employee_required` would give 403, and `LoginRequiredMixin` where the employee-record gate belongs — but it neither leaks nor 500s.
- **Target 6 — the Postgres-specific paths are sound.** The `LIKE` case-sensitivity concern is disconfirmed by reading: `apps/home/views.py:1225-1226` already uses `email__iexact`. The analytics dashboard, XLSX export and evaluation list were all driven with zero `ScholarshipApplication` rows and pass, including the `PercentileCont` ordered-set aggregate.

**The auth × host matrix is otherwise clean.** `AuthHostMatrixSweepTests` walks 21 public, 5 staff and 5 student paths across all four auth states on all three hosts using `subTest`. No 5xx anywhere.

## Correction on record

Mid-session I stated that the navbar 500s for any logged-in employee browsing the ordinary public site. **That was wrong.** Both `{% url 'staff:profile_update' %}` occurrences (`navbar.html:34`, `:314`) sit inside `{% if 'staff' in host %}` (`navbar.html:17`, `:301`), so the block never renders on `lvh.me`. The matrix sweep is what caught it.

The real defect is narrower and is recorded as Finding 7: `'staff' in host` is a substring test, so any allowed host merely *containing* "staff" renders the block while the middleware routes the request to `main.urls`, where the `staff:` namespace does not exist. Three passing pins record the safe cases.

## Test-database caveat

Finding 1 blocked the sanctioned strategy outright, so it was raised before proceeding. With approval, the suite runs against a throwaway settings module in the session scratchpad, **outside the repo**, which does nothing but `from main.settings import *` plus a `MIGRATION_MODULES` stub:

```
manage.py test apps --settings=nomig_settings --noinput
```

with that directory on `PYTHONPATH`. Still local Postgres; Neon remains unreachable.

**Consequence:** data migrations do not run under test, so any 500 that depends on migration-seeded data would not have reproduced. None of the eight findings depend on seeded data, but the sweep is not exhaustive in that respect. A stale `test_uon_alumni_II` from the aborted first run was dropped, with approval.
